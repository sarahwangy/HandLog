第一站：浏览器怎么录音

这段代码来自 src/hooks/useWhisper.ts——它负责问你的手机要麦克风权限、录音、再把录音送出去。

CODE 

const startRecording = async () => {
  const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
  const mimeType = MediaRecorder.isTypeSupported("audio/mp4")
    ? "audio/mp4"
    : "audio/webm";
  const recorder = new MediaRecorder(stream, { mimeType });
  recorder.onstop = async () => {
    const audioBlob = new Blob(chunks, { type: mimeType });
    const formData = new FormData();
    formData.append("audio", audioBlob);
    const response = await fetch("/api/transcribe", {
      method: "POST",
      body: formData,
    });
  };
  recorder.start();
};
PLAIN ENGLISH

开始录音这件事，是一个异步过程——要等手机的麦克风权限批下来才能继续。

向浏览器申请麦克风权限，得到一条"声音数据流"。

检查手机支持哪种音频格式，优先用 mp4，不支持就退而求其次用 webm。

用拿到的格式，创建一个真正的"录音机"对象。

当你点击"停止录音"时，把录到的声音打包成一个音频文件（Blob）。

再把这个音频文件塞进一个"表单包裹"（FormData）里，方便通过网络送出去。

把这个包裹寄给后端的 /api/transcribe 地址，也就是"耳朵"的接待窗口。

用 POST 方式发送——意味着"我要交给你一些数据"，不是单纯"问你要数据"。

最后，按下"开始录音"按钮，一切才真正启动。

演员的日常：自动保存草稿

这是 useAutosave.ts 里真实的一小段——一个专门负责"你停止打字 3 秒后自动存草稿"的hook。

CODE 

if (timerRef.current) clearTimeout(timerRef.current);

setStatus("idle"); // 重置为 idle，等待下一次保存

timerRef.current = setTimeout(() => {
  save(content);
}, delay);
PLAIN ENGLISH

如果上一个"倒计时"还没响，先取消它——不然会存好几次重复的草稿。

把保存状态标成"还没存"，让界面上能显示出来。

重新开始一个倒计时：等 delay（默认 3000 毫秒，也就是 3 秒）之后，再真正去保存。

这种"每次输入都重新计时，停下来才真正执行"的写法，业内叫防抖（debounce）——你敲键盘越快，它越"忍着不存"，直到你停下来。

💡
关键洞察

把"检查权限"和"处理交互"拆成两个文件，是工程里的重要原则——业内叫"关注点分离"。这也是为什么 HandLog 把 Claude 调用逻辑单独放进 lib/claude.ts，而不是直接写在 CaptureForm.tsx 里。

数据怎么流动——从一段文字到 Notion 里的一个折叠块

你在 Notion 里点开的那个"复盘"折叠框，其实是程序分两次快递才"造"出来的

先想象一次快递打包

你的日记文字，就像一件要寄出的商品。Claude 把它"打包"成一个标准化的包裹——这个包裹在程序世界里有个名字，叫 JSON。

但快递偶尔会"包装变形"——AI 写出来的 JSON 有时候不完全合规。Notion 这位收货员，还得会一手"拆歪包装"的绝活，才能把东西正确放进你笔记本的格子里。

质检员的第一招：只剪最外层完整的包裹

Claude 有时候会在 JSON 前后多说几句客套话，比如"好的，这是你的复盘："。extractJson 不会傻乎乎地找最后一个 大括号， 而是用"括号计数法"精确数出真正闭合的那一个。

CODE 

// 从 Claude 的响应里提取 JSON 对象，忽略前后多余的文字或 markdown 代码块
function extractJson(text: string): string {
  const start = text.indexOf("{");
  if (start === -1) throw new Error("No JSON object found in response");

  // 用括号计数法找到真正匹配的根级闭合括号，而不是 lastIndexOf
  let depth = 0;
  let inString = false;
  let escape = false;
  for (let i = start; i < text.length; i++) {
    const ch = text[i];
    if (escape) { escape = false; continue; }
    if (ch === "\\" && inString) { escape = true; continue; }
    if (ch === '"') { inString = !inString; continue; }
    if (inString) continue;
    if (ch === "{") depth++;
    else if (ch === "}") {
      depth--;
      if (depth === 0) return text.slice(start, i + 1);
    }
  }
  throw new Error("JSON object not properly closed (truncated response)");
}
PLAIN ENGLISH

先找到第一个 { ——包裹的开箱位置。没找到就直接报错，说明这次没打包出任何东西。

准备一个计数器 depth，从 0 开始；另外记录"现在是不是在一段引号字符串里面"。

逐个字符扫描：如果在字符串里，先原样跳过（字符串里的花括号不算数，比如日记正文里写的表情符号或符号）。

碰到 { 就把计数器加一，碰到 } 就减一——每一层花括号都被记一笔账。

当计数器第一次回到 0，说明最外层的包裹刚好在这里闭合——把这一段截出来就是完整、干净的 JSON，不用管后面 Claude 还说了什么客套话。

最后一关：造一个可以点开的"复盘"折叠框

你在 Notion 看到的那个可以点开的 折叠块（Toggle）， 外面是个能点开的壳，里面套了一个带图标的 高亮块（Callout） ——这两层是分两次 API 调用才造出来的，不是一次搞定。

1
先造一个空盒子

调用一次 API，在页面里建一个 Toggle，Toggle 里放一个内容还是空的 Callout——这时候程序还不知道这个 Callout 真正的编号（ID）是什么。

2
回头查一下盒子的编号

再调用一次 API，去问 Notion："刚才那个 Toggle 里面，你给它装的 Callout 编号是多少？"——拿到真正的 ID，才能往里塞东西。

3
把复盘内容塞进去

评分、感悟、下一步这些内容块，最后都追加到这个真正拿到手的 Callout 编号下面，你才会在 Notion 里看到点开折叠框有完整内容。

CODE · Step 1

调用 Notion 的 API，往这个页面里追加一块内容。

要加的内容是一个 Toggle（折叠块），标题写"周X复盘"，加粗显示。

这个 Toggle 里面预先塞了一个空的 Callout（高亮块），带个 📋 图标——先当个占位的空盒子。

CODE · Step 2 

// Step 2：找到刚建的 Toggle 里的 Callout ID
const toggleId = toggleRes.results[0]?.id;
if (!toggleId) return;

const toggleChildren = await withAuthCheck(() =>
  notion.blocks.children.list({ block_id: toggleId })
) as { results: { id: string; type: string }[] };

const calloutId = toggleChildren.results.find(b => b.type === "callout")?.id;
if (!calloutId) return;

从第一次 API 调用的返回结果里，拿到刚创建的 Toggle 自己的编号。如果没拿到就直接放弃（说明创建失败）。

再发一次 API 请求，问 Notion："这个 Toggle 底下都有哪些子内容？"——这才是第二次真正的网络请求。

在返回的子内容列表里，找到类型是 "callout" 的那一个，取出它的真实编号。

有了这个真实编号，后面才能放心地往这个 Callout 里追加评分、感悟、下一步这些内容。

Notion 的"每次最多搬 100 件"规则

Notion 的 API 有个硬性限制：一次最多只能往一个页面里追加 100 个内容块。HandLog 用一个小函数悄悄绕开了这个限制。

代码 

// Notion API 每次 append 最多 100 个 block，超过会报错。这个函数自动分批处理。
async function batchAppend(notion, blockId, blocks) {
  const CHUNK = 100;
  for (let i = 0; i < blocks.length; i += CHUNK) {
    await withAuthCheck(() =>
      notion.blocks.children.append({ block_id: blockId, children: blocks.slice(i, i + CHUNK) })
    );
  }
}
大白话

先把"每趟最多搬多少件"定成一个数字：100。

用一个循环，每次往前挪 100 件，一趟一趟地搬，直到全部搬完。

每一趟都单独发一次请求给 Notion，只带上这一批的内容块。

哪怕日记再长、生成的块再多，Notion 那边也永远只看到"每次不超过 100 个"。

两种"保质期"，两个理由

草稿和 Notion 数据缓存都存在同一个地方，但管家给它们设置了完全不同的过期时间。

代码 

const DRAFT_TTL = 60 * 60 * 24 * 7; // 7 days
const CACHE_TTL = 60 * 5;            // 5 minutes
大白话

草稿的 TTL 是 7 天——因为这是你手写还没提交的东西，丢了没法找回，宁可多留一阵子。

Notion 数据的缓存只留 5 分钟——因为这份数据随时能重新问 Notion 要一份新的，留太久反而可能是过期信息。

另一个"统一拦截"的小聪明：把所有 Notion 调用都包一层，专门盯着一种错误—— 401。

代码 

async function withAuthCheck<T>(fn: () => Promise<T>): Promise<T> {
  try {
    return await fn();
  } catch (error: unknown) {
    if (
      typeof error === "object" &&
      error !== null &&
      "status" in error &&
      (error as { status: number }).status === 401
    ) {
      throw new NotionAuthError();
    }
    throw error;
  }
}
大白话

这个函数把"真正要做的 Notion 调用"包在 try 里执行。

一旦出错，先检查这个错误是不是"401 未授权"——也就是用户在 Notion 后台把授权撤销了。

如果是，就统一抛出一个自定义的 NotionAuthError，让上层代码能识别"要引导用户重新连接"。

如果不是 401，就把错误原样往外抛——不吞掉任何意外情况。

💡
为什么要"统一包一层"

如果没有 withAuthCheck，每一个调用 Notion 的函数都要自己重复写一遍"检查 401、判断要不要报特殊错误"的逻辑——多一个新函数就多一处可能忘记写的地方。包一层之后，这个规则只用维护一次。

验房报告：这栋房子的裂缝在哪

买房前请验房师来挑毛病，不是为了劝退你，而是让你带着清单住进去。这是 HandLog 的验房报告，也是这门课的最后一站。

一个会骗人的名字

如果你去翻 HandLog 的代码，会发现一个叫 /api/handlog/generate 的路由——名字听起来像"生成日记"，但它实际上是用来画画的。

名字有时候会骗人。这一模块，我们像验房师一样，把 HandLog 里容易让新手迷惑的细节一条条挑出来。

🔍
真实项目 ≠ 教科书例子

真实代码会有命名不准确、文档过时、"预留但没用上"的设计。学会识别这些不完美，是从"看得懂代码"到"能独立debug"的关键一步。

坑一：同名不同姓，同姓不同名

两个路由的名字和实际功能对不上号——这是最容易让新手在真实项目里迷路的地方。

/api/handlog/generate 名字像"生成日记"，实际是调用 OpenAI 画一张手绘复盘图
/api/process 名字很朴素，实际才是真正"生成复盘"的那个路由
💡
关键洞察

命名不是文档，代码本身才是唯一可信的来源。下次遇到"望文生义"的函数名或路由名，先打开文件看它实际在做什么，别只信名字。

坑二：一个靠"约定"撑着的字符串

这段代码来自 src/lib/claude.ts——它靠 weekLabel 这个字符串必须长成固定格式，才能正确拆出月份和日期。

CODE 

const parts = weekLabel.split("-");
const month = parts[0];
const startDay = parseInt(parts[1]);
PLAIN ENGLISH

把 weekLabel（长得像 "5-4-10"，意思是 5 月 4 日到 10 日）按"-"切成几段。

默认第一段就是月份——这里没做任何检查。

默认第二段就是起始日期，直接转成数字用。

⚠️
脆弱的字符串协议

这段代码依赖固定格式的字符串协议：如果 weekLabel 的格式对不上，这里不会报错提醒你，只会静默产生错误的日期。

坑三：两套认证机制，只有一套真的在用

HandLog 里同时存在两种"跟 Notion 打交道"的设计——但目前只有一种真正被激活。

✅

Internal Token（真正在用）

src/lib/auth.ts 里的 getNotionTokenInternal()——直接从环境变量读一个固定 Token，只服务这一个用户。

🚧

多用户 OAuth（预留未激活）

src/lib/notion-schema.ts 里的 NotionUserSchema——为"每个用户有自己的 Notion 数据库"设计的字段映射结构，但目前没有被真正接入认证流程。

🧭
好在哪

这是一种常见的工程习惯：先把"未来可能需要"的结构写出来占位，但先用最简单的方式跑通。看到"两条路同时存在"，先搞清楚哪条是真正被调用的，别被没被激活的那条绕晕。

坑四：先创建，再回查（复习）

Module 3 详细讲过：notion.ts 里的 appendReviewBlocks 得先创建 Toggle 和 Callout 两个区块，再回头查它们的 id，才能把内容正确写进去。

🔁
不是 HandLog 特有的坑

这其实是 Notion API 的通用限制——它的设计就是"先创建空壳，再补内容"，任何调用 Notion API 写复杂结构的项目都得处理这一步，不是 HandLog 独有的毛病。

坑五：交接班用的是一张便利贴

录音页面生成复盘后，要把结果"带"到复盘页面去。HandLog 用的是浏览器的 sessionStorage，像在两个房间之间传一张便利贴。

CODE — CaptureForm.tsx 

// 把复盘结果存到 sessionStorage，Review 页面从这里读
sessionStorage.setItem("pendingReview", JSON.stringify(review));
router.push(`/${locale}/review`);
PLAIN ENGLISH

把刚生成的复盘结果，写进这张"便利贴"，贴的名字叫 pendingReview。

再把用户带到复盘页面去——那边的代码会去找这张便利贴。

CODE — ReviewContent.tsx 

// 页面加载时先检查 sessionStorage 里有没有从 Capture 页传来的复盘结果
const pending = sessionStorage.getItem("pendingReview");
if (pending) {
  const parsed = JSON.parse(pending);
  setReview(parsed);
  sessionStorage.removeItem("pendingReview");
}
PLAIN ENGLISH

复盘页面一打开，先去便利贴那里瞅一眼有没有东西。

如果有——

就把它读出来解析成数据。

显示到页面上。

看完立刻把便利贴撕掉，避免下次进来看到过期数据。

⚠️
便利贴的局限

sessionStorage 只在当前标签页有效——用户如果直接把复盘页面的链接分享给自己、换个浏览器标签页打开，便利贴就是空的。这是一种"够用但不完美"的取巧方案，本质上是前端页面间传数据的常见权宜之计。
