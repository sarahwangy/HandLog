聪明的工程技巧——一个精明管家的省钱哲学

好管家不会每件事都用最贵的方式做——HandLog 的代码里，藏着好几个这样的小聪明

想象一个精明的管家

一个好管家不会每次都请最贵的师傅办事——日常小事交给便宜的帮手，重要场合才请真正的高手。东西太多一次搬不完，就分几趟搬；不同东西也有不同的"保质期"。

💡
一个真实的数字

HandLog 生成"月复盘"的时候，并没有把整整 30 天的日记一天天喂给 Claude——这个设计选择，一年能省下不少 token 费用。这一模块就来拆解这些"管家智慧"。

四张"管家的小聪明"卡片

好工程不是"能跑就行"，而是在成本、速度、可靠性之间做出刻意的权衡。下面这四张卡片，就是 HandLog 里最典型的四个权衡。

🎩

模型分级

重要的日/周复盘请贵一点的 模型 帮忙，简单的提取小任务交给便宜的模型——省钱。

📦

整月一次打包

不是每天叫一次 AI，而是把一整月的内容打包成一次 API 调用 ——省钱效果更明显。

🚚

分批搬运

Notion 一次最多只肯收 100 件"包裹"，东西多的话就分几趟搬，一次超限报错都不会有。

⏳

双保质期缓存

草稿留 7 天防止你没保存就白写， 缓存 数据只留 5 分钟，因为随时能重新问 Notion 要。

日/周复盘要写得有洞察力，值得请贵一点的模型；从日记里挑几个关键词这种粗活，便宜模型完全够用。

管家的判断标准

不是"这个任务重不重要"，而是"这个任务需不需要深度理解"。表格提取、关键词抽取这类结构化小活，便宜模型往往就能做好。

Notion 的"每次最多搬 100 件"规则

Notion 的 API 有个硬性限制：一次最多只能往一个页面里追加 100 个内容块。HandLog 用一个小函数悄悄绕开了这个限制。

代码 

// Notion API 每次 append 最多 100 个 block，超过会报错。这个函数自动分批处理。
async function batchAppend(notion, blockId, blocks) {
  const CHUNK = 100;
  for (let i = 0; i < blocks.length; i += CHUNK) {
    await withAuthCheck(() =>
      notion.blocks.children.append({ block_id: blockId, children: blocks.slice(i, i + CHUNK) })
    );
  }
}
大白话

先把"每趟最多搬多少件"定成一个数字：100。

用一个循环，每次往前挪 100 件，一趟一趟地搬，直到全部搬完。

每一趟都单独发一次请求给 Notion，只带上这一批的内容块。

哪怕日记再长、生成的块再多，Notion 那边也永远只看到"每次不超过 100 个"。

两种"保质期"，两个理由

草稿和 Notion 数据缓存都存在同一个地方，但管家给它们设置了完全不同的过期时间。

代码 

const DRAFT_TTL = 60 * 60 * 24 * 7; // 7 days
const CACHE_TTL = 60 * 5;            // 5 minutes
大白话

草稿的 TTL 是 7 天——因为这是你手写还没提交的东西，丢了没法找回，宁可多留一阵子。

Notion 数据的缓存只留 5 分钟——因为这份数据随时能重新问 Notion 要一份新的，留太久反而可能是过期信息。

另一个"统一拦截"的小聪明：把所有 Notion 调用都包一层，专门盯着一种错误—— 401。

代码 

async function withAuthCheck<T>(fn: () => Promise<T>): Promise<T> {
  try {
    return await fn();
  } catch (error: unknown) {
    if (
      typeof error === "object" &&
      error !== null &&
      "status" in error &&
      (error as { status: number }).status === 401
    ) {
      throw new NotionAuthError();
    }
    throw error;
  }
}
大白话

这个函数把"真正要做的 Notion 调用"包在 try 里执行。

一旦出错，先检查这个错误是不是"401 未授权"——也就是用户在 Notion 后台把授权撤销了。

如果是，就统一抛出一个自定义的 NotionAuthError，让上层代码能识别"要引导用户重新连接"。

如果不是 401，就把错误原样往外抛——不吞掉任何意外情况。

💡
为什么要"统一包一层"

如果没有 withAuthCheck，每一个调用 Notion 的函数都要自己重复写一遍"检查 401、判断要不要报特殊错误"的逻辑——多一个新函数就多一处可能忘记写的地方。包一层之后，这个规则只用维护一次。
