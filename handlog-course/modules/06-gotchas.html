验房报告：这栋房子的裂缝在哪

买房前请验房师来挑毛病，不是为了劝退你，而是让你带着清单住进去。这是 HandLog 的验房报告，也是这门课的最后一站。

一个会骗人的名字

如果你去翻 HandLog 的代码，会发现一个叫 /api/handlog/generate 的路由——名字听起来像"生成日记"，但它实际上是用来画画的。

名字有时候会骗人。这一模块，我们像验房师一样，把 HandLog 里容易让新手迷惑的细节一条条挑出来。

🔍
真实项目 ≠ 教科书例子

真实代码会有命名不准确、文档过时、"预留但没用上"的设计。学会识别这些不完美，是从"看得懂代码"到"能独立debug"的关键一步。

坑一：同名不同姓，同姓不同名

两个路由的名字和实际功能对不上号——这是最容易让新手在真实项目里迷路的地方。

/api/handlog/generate 名字像"生成日记"，实际是调用 OpenAI 画一张手绘复盘图
/api/process 名字很朴素，实际才是真正"生成复盘"的那个路由
💡
关键洞察

命名不是文档，代码本身才是唯一可信的来源。下次遇到"望文生义"的函数名或路由名，先打开文件看它实际在做什么，别只信名字。

坑二：一个靠"约定"撑着的字符串

这段代码来自 src/lib/claude.ts——它靠 weekLabel 这个字符串必须长成固定格式，才能正确拆出月份和日期。

CODE 

const parts = weekLabel.split("-");
const month = parts[0];
const startDay = parseInt(parts[1]);
PLAIN ENGLISH

把 weekLabel（长得像 "5-4-10"，意思是 5 月 4 日到 10 日）按"-"切成几段。

默认第一段就是月份——这里没做任何检查。

默认第二段就是起始日期，直接转成数字用。

⚠️
脆弱的字符串协议

这段代码依赖固定格式的字符串协议：如果 weekLabel 的格式对不上，这里不会报错提醒你，只会静默产生错误的日期。

坑三：两套认证机制，只有一套真的在用

HandLog 里同时存在两种"跟 Notion 打交道"的设计——但目前只有一种真正被激活。

✅

Internal Token（真正在用）

src/lib/auth.ts 里的 getNotionTokenInternal()——直接从环境变量读一个固定 Token，只服务这一个用户。

🚧

多用户 OAuth（预留未激活）

src/lib/notion-schema.ts 里的 NotionUserSchema——为"每个用户有自己的 Notion 数据库"设计的字段映射结构，但目前没有被真正接入认证流程。

🧭
好在哪

这是一种常见的工程习惯：先把"未来可能需要"的结构写出来占位，但先用最简单的方式跑通。看到"两条路同时存在"，先搞清楚哪条是真正被调用的，别被没被激活的那条绕晕。

坑四：先创建，再回查（复习）

Module 3 详细讲过：notion.ts 里的 appendReviewBlocks 得先创建 Toggle 和 Callout 两个区块，再回头查它们的 id，才能把内容正确写进去。

🔁
不是 HandLog 特有的坑

这其实是 Notion API 的通用限制——它的设计就是"先创建空壳，再补内容"，任何调用 Notion API 写复杂结构的项目都得处理这一步，不是 HandLog 独有的毛病。

坑五：交接班用的是一张便利贴

录音页面生成复盘后，要把结果"带"到复盘页面去。HandLog 用的是浏览器的 sessionStorage，像在两个房间之间传一张便利贴。

CODE — CaptureForm.tsx 

// 把复盘结果存到 sessionStorage，Review 页面从这里读
sessionStorage.setItem("pendingReview", JSON.stringify(review));
router.push(`/${locale}/review`);
PLAIN ENGLISH

把刚生成的复盘结果，写进这张"便利贴"，贴的名字叫 pendingReview。

再把用户带到复盘页面去——那边的代码会去找这张便利贴。

CODE — ReviewContent.tsx 

// 页面加载时先检查 sessionStorage 里有没有从 Capture 页传来的复盘结果
const pending = sessionStorage.getItem("pendingReview");
if (pending) {
  const parsed = JSON.parse(pending);
  setReview(parsed);
  sessionStorage.removeItem("pendingReview");
}
PLAIN ENGLISH

复盘页面一打开，先去便利贴那里瞅一眼有没有东西。

如果有——

就把它读出来解析成数据。

显示到页面上。

看完立刻把便利贴撕掉，避免下次进来看到过期数据。

⚠️
便利贴的局限

sessionStorage 只在当前标签页有效——用户如果直接把复盘页面的链接分享给自己、换个浏览器标签页打开，便利贴就是空的。这是一种"够用但不完美"的取巧方案，本质上是前端页面间传数据的常见权宜之计。

收尾两个小提醒

📄
文档会滞后于代码

项目约定里提到要遵守 docs/notion.md，但这个文件在代码库里其实不存在——真正的字段映射定义在 src/lib/notion-schema.ts 里。文档过时是真实项目的常态，代码才是最终真相。

🚪
开发环境的"后门"

本地开发时（NODE_ENV === "development"），有几个路由会跳过登录校验，方便调试。这很方便，但上线前一定要再三确认这个判断真的只在开发环境生效，别把后门带上线。
